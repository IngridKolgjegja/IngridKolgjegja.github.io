Power BI Star Schema Explained

A star schema is one of the most common and useful ways to organise data in Power BI. It helps keep your model easier to understand, easier to filter and often easier to maintain.

What is a star schema?

A star schema usually has one central fact table connected to several dimension tables. 

         Customers
             |
             |
Products — Sales — Calendar
             |
             |
          Regions

The fact table sits in the centre, while dimension tables surround it.

What is a fact table?

A fact table contains the events or transactions you want to analyse.

For example, a sales fact table could contain:

  • Order ID
  • Date ID
  • Product ID
  • Customer ID
  • Quantity
  • Sales Amount

A fact table usually contains many rows.

What is a dimension table?

A dimension table contains descriptive information used to filter or group the fact table.

Examples include:

  • Products
  • Customers
  • Calendar
  • Regions
  • Stores

A product dimension might contain: 

ProductID
ProductName
Category
Brand

How fact and dimension tables connect

Dimension tables normally connect to the fact table using one-to-many relationships. 

Products[ProductID]  1 → *  Sales[ProductID]

Each product appears once in the Products table, but it can appear many times in the Sales table.

Why use a star schema?

1. Easier filtering

Dimension tables can filter the fact table in a predictable way.

For example, a slicer using: 

Products[Category]

can filter sales by category.

2. Cleaner DAX

Measures are usually easier to write when your model follows a clear structure.

3. Easier maintenance

A well-structured model is easier to understand when you return to it later or when another person needs to work with it.

4. Better report design

You can use dimension fields for slicers and categories while keeping numeric calculations in the fact table.

Useful rule: use dimensions to describe and filter your data, and fact tables to store the events and values you want to measure.

Example model

Imagine a retail report.

Your central table could be: 

FACT_SALES

connected to: 

DIM_PRODUCT
DIM_CUSTOMER
DIM_DATE
DIM_STORE

This allows you to analyse total sales by:

  • product
  • customer
  • month
  • store

Common mistake: one large flat table

Beginners often import one large table containing every field.

For example: 

Date
Customer
Customer Country
Product
Product Category
Store
Sales Amount

This may work for small reports, but as the model becomes more complex it can be harder to manage.

Separating descriptive fields into dimensions usually gives the model a clearer structure.

Common mistake: dimension-to-dimension chains

A clean star schema usually connects dimensions directly to the fact table rather than creating long chains of tables.

Simpler relationship paths are generally easier to understand and troubleshoot.

Star schema vs snowflake schema

In a star schema, dimension tables connect directly to the fact table.

In a snowflake schema, dimensions may be split into additional related tables.

Power BI can work with both structures, but a simpler star schema is often easier to use for reporting.

Quick checklist

  • Do you have a clear central fact table?
  • Are descriptive fields stored in dimension tables?
  • Do dimensions contain unique keys?
  • Are relationships mostly one-to-many?
  • Are slicers using dimension fields?
  • Is the model easy to understand visually?
